# Spike: WebKit vs 네이티브 UI 비교 실험 (계획, 2026-10-13)

> UI를 WebKit(wry)에서 macOS 네이티브로 바꿀지 정하기 위한 실험이다. 같은 기능을 네 방식으로 만들어 수치로 비교한다. 결과는 이 문서 아래에 채운다. `spike/` 경로는 결론이 난 뒤 정리한다.

## 왜 지금인가
- M1-6 측정에서 RSS의 대부분(약 150MB)이 WebKit 프로세스 3개였다. 작은 diff도 약 200MB라 PRD §8의 250MB 기준이 경계에 걸렸다
- UI에 묶인 코드는 아직 약 650줄이다(`src/app` 313줄, `protocol.rs`, `events.rs` 일부, `main.rs`). 나머지 백엔드(`args`, `git`, `diff`, `store`, `config`, `Review`, `File::rows`)는 그대로 쓴다
- 지난 스파이크(SPIKE-rust-vs-tinyjs)는 둘 다 WebKit이었다. 네이티브는 비교한 적이 없다
- PRD에서 Linux와 Windows는 비목표다. 그래서 macOS 전용이 되어도 된다

## 비교 대상
| 이름 | 구성 | 빌드 |
|---|---|---|
| **W** (기준) | 현재 코드: Rust + wry 0.57 + WKWebView, 가상 스크롤, 1,000행 청크 | `cargo build --release` |
| **A** `spike/a-appkit-rs/` | Rust + objc2 0.6 / objc2-app-kit 0.3. `NSSplitView` + `NSOutlineView`(트리) + view-based `NSTableView`(diff). 델리게이트는 `define_class!` | `cargo build --release` |
| **B** `spike/b-appkit-swift/` | Swift 6 AppKit UI(구성은 A와 같다) + Rust 코어 staticlib. 경계는 작은 C ABI(리뷰 열기, 파일 요약, `rows(file, from, n)`를 JSON 문자열로)다. UniFFI는 스파이크 범위에서 빼고 보고서에 비용만 적는다 | `cargo build` + `swiftc` (스크립트 1개) |
| **C** `spike/c-gpu-rs/` | Rust GPU UI. **gpui**(Zed의 프레임워크, 코드 텍스트 렌더에 특화)가 crates.io에서 받아지고 빌드가 30분 안에 되면 gpui, 아니면 **egui/eframe**. 무엇을 골랐는지와 그 이유를 기록한다 | `cargo build --release` |

모든 버전은 `griiy` 크레이트를 path 의존성으로 가져와 **같은 `Review::open`과 같은 행 모델**을 쓴다. 네이티브는 JSON 없이 구조체를 직접 읽는다. B만 C ABI 경계에서 JSON을 쓴다.

## 공통 기능 (W의 M1-5/6 화면과 같게)
1. `<bin> -C <repo> [range]`: 인자 파싱은 `griiy::args`를 쓴다
2. 헤더: 저장소 경로, 범위 라벨, `n changed / m files`
3. 왼쪽 트리: 추적 파일 전체, 변경 파일에 `+a -d`, 변경이 있는 폴더만 펼침, 자식이 하나뿐인 폴더 체인 합치기. 클릭하면 diff의 해당 파일로 이동한다
4. 오른쪽 diff: 파일 헤더 행(상태 글자, rename `old → new`, `+a -d`), hunk 헤더, 줄(old/new 줄 번호 두 칸, 추가·삭제 배경색), 개행 없음 표시, hunk 없는 파일의 설명 행. 고정 높이 행, 보이는 행만 그림, 가로 스크롤
5. 에러 화면: `Review::open`이 실패하면 제목, 상세, 힌트
6. 다크 모드: 시스템 설정을 따른다

하지 않는 것: 구문 강조, 검색, 단축키, 헤더 고정(sticky), 봤음 체크.

## 위험 확인 (짧게, 각 버전에서)
본 기능 다음으로 이후 작업에서 가장 위험한 두 가지만 확인한다.
- **R-MD PR Markdown 안전 렌더 (F-PR-5):** M2-4의 악성 fixture(`<script>`, `<img onerror>`, `javascript:` 링크, 외부 이미지, iframe)를 별도 창이나 패널에 렌더한다. 스크립트가 실행되지 않는지, 외부 요청이 없는지, https 링크만 살아 있는지, 원본 HTML이 글자로 보이는지 확인한다
  - A/B는 `NSAttributedString` markdown 초기화를, C는 해당 프레임워크의 markdown 위젯(없으면 "없음"으로 기록)을 쓴다
- **R-SEL 줄 드래그 선택 (F-AI-1):** diff에서 여러 행을 드래그하면 화면 밖으로 스크롤되는 범위까지 선택이 유지되는지 본다. 결과 `Selection { path, side, start, end }`를 stderr로 출력하고, 선택한 행은 강조한다
- **Mermaid(M7)는 시험하지 않는다.** 네이티브라면 Explain 탭에만 WKWebView를 지연 생성하는 혼합 구조를 전제로 하고, 그 비용(이 탭을 열 때만 WebKit 메모리)을 보고서에 적는다

## 측정 (W와 같은 방법, 같은 기계, 순서대로)
- **저장소:** 작은 diff(griiy `HEAD~1..HEAD`, 약 900행), 15만 줄·300파일(`big120k`), 12만 줄·1파일(`one120k`), 1만 파일 트리(합성 `bigtree`)
- **bench 프로토콜은 W와 같다:** `GRIIY_MARK` 파일에 JSON 줄 2개를 쓴다
  - **1줄 = 첫 페인트:** 실제 행이 화면에 그려진 뒤의 첫 프레임
  - **2줄 = 자동 스크롤:** 10곳으로 점프한 뒤 각 위치에서 60프레임씩 화면 절반 속도로 스크롤. 프레임 간격(첫 10프레임과 점프 직후 2프레임 제외), 50ms 초과 수, 최대 프레임, 화면에 있는 행 뷰 수 최대
  - 프레임 간격은 W는 rAF, A/B는 `NSView.displayLink`(CADisplayLink, macOS 14+) 콜백, C는 프레임 루프로 잰다
  - 측정 스크립트는 `spike/bench.sh` 하나다. 현재 `bench.sh`와 같은 방식에 APPS 목록만 다르다
- **항목:**
  1. **빌드:** 클린 빌드 시간, 증분 빌드(UI 파일 한 줄 수정) 시간, 중간 산출물 크기, 필요한 툴체인
  2. **배포물:** 파일 수, 바이너리 크기, 단독 복사 시 실행되는가, `cargo install` 가능한가, `otool -L`
  3. **속도:** 실행→첫 페인트(웜 3회, 콜드 1회 별도 표기), 스크롤 50ms 초과 프레임, 최대 프레임
  4. **메모리:** 프로세스별 RSS 합(W는 WebKit 헬퍼 포함)과 앱의 `vmmap` physical footprint. 둘 다 자동 스크롤 1초 뒤에 잰다
  5. **기능:** 창 하나만 `screencapture -l <CGWindowID>`로 찍어 공통 기능 1~6과 R-MD, R-SEL 결과를 확인한다. **화면 전체 캡처는 하지 않는다**
  6. **코드:** UI 코드 줄 수, 막혔던 지점, 문서·예제 접근성(주관 평가는 짧게)

## 진행 방식
- A, B, C를 에이전트 3개가 **병렬로** 만든다(각자 자기 디렉터리만 건드린다). W와 `src/`는 건드리지 않는다
- 각 버전은 테스트 저장소 4개에서 실행해 보고 bench 2줄이 나오는지 확인한 뒤 보고한다. 측정은 내가 한 기계에서 순서대로 한다(병렬 측정은 서로 간섭한다)
- 시간 제한: 버전당 에이전트 작업 한 번. 막히면 막힌 지점과 그때까지의 결과를 그대로 보고한다(그것도 결과다)
- 구현 리뷰는 하지 않는다(버릴 코드). 대신 **측정 방법과 결론**을 fable이 검토한다

## 판단 기준 (결과를 보기 전에 정해 둔다)
네이티브로 바꾸려면 아래를 모두 만족해야 한다.
1. 15만 줄에서 첫 화면이 W와 같거나 빠르고(≤ 0.6s), 스크롤 50ms 초과 프레임이 ≤ 1%
2. 메모리(RSS 합)가 W보다 **100MB 이상** 적다. 그렇지 않으면 바꾸는 비용에 비해 이득이 작다
3. R-MD가 안전하게 된다. R-SEL이 W보다 어렵지 않다
4. 배포가 PRD를 지킨다: 실행 파일 하나(또는 `.app` + 심링크, M0-3), 바이너리 < 15MB
5. UI 코드량과 유지 비용이 W의 2배를 넘지 않는다(주관 포함, 근거와 함께 적는다)

## 계획 리뷰 반영 (codex, fable · 2026-10-13). 위 계획보다 우선한다

### 사용자 결정
- **C = gpui, D = egui/eframe 둘 다 만든다.** gpui는 Xcode 26에서 Metal 툴체인을 따로 받아야 빌드된다. 그래서 사용자 승인을 받아 `xcodebuild -downloadComponent MetalToolchain`으로 받았다(Metal Toolchain 27A266a). 이 의존성은 그대로 배포 조건에 남는다. gpui를 채택하면 `cargo install` 사용자 모두에게 Xcode와 Metal 툴체인이 필요하다
- **B는 A와 같은 풀 앱이다** (트리, diff, 프로브까지)

### 측정 (`spike/bench.sh`, 모든 버전 공통)
- **첫 화면** = 실행부터 **실제 diff 행이 그려진 뒤의 첫 표시 틱**까지. 앱이 그 시점의 벽시계(epoch ms)를 mark 1줄의 `wall`에 넣고, bench가 실행 시각을 뺀다. 폴링 오차가 없다
  - W: rAF 뒤 `Date.now()`
  - A/B: 행 뷰가 채워진 뒤의 첫 displayLink 콜백
  - C/D: 행을 그린 프레임의 다음 프레임
- **git은 모든 버전이 W처럼 백그라운드 스레드에서 창 생성과 병렬로 돈다.** 그렇지 않으면 git 시간이 네이티브에만 직렬로 더해진다
- **스크롤 프레임:** 좋은 프레임은 "50ms 미만이고 blank가 아님"이다. W는 청크 fetch 지연이 blank로, 네이티브는 메인 스레드 동기 `rows()`가 긴 프레임으로 나타나기 때문이다. 둘을 함께 센다. C/D는 자동 스크롤 동안 매 프레임 다시 그리기를 요청한다
- **메모리:**
  - 주 지표는 `/usr/bin/footprint`의 `phys_footprint` 합이다. 앱과 그 자식, 그리고 W라면 새로 뜬 WebKit 헬퍼 3개를 더한다(헬퍼가 0개도 3개도 아니면 FAILED)
  - 자동 스크롤이 끝나고 5초 뒤 1초 간격으로 3번 재서 중앙값을 쓴다
  - RSS 합은 참고로만 적는다(공유 페이지를 프로세스마다 중복으로 센다. W의 RSS 합 약 200MB 중 절반 가까이가 중복이다)
- **순서와 판정:** 라운드마다 버전 순서를 섞는다. 콜드 스타트는 재지 않는다(재부팅 없이는 통제가 안 된다). 판정은 5라운드의 중앙값과 범위로 한다
- **고정:** 창 1100×720, 행 18px, 같은 디스플레이·전원 상태. 디스플레이 해상도와 주사율을 기록한다

### 프로브 (R-MD, R-SEL 대체·추가)
- **P-MD Markdown 렌더 비용:** 안전성은 AppKit에서 거의 공짜다(fable이 확인: `<script>`·`<img onerror>`·`<iframe>`이 글자로 남고, 이미지는 자동 로드가 없다). 대신 `javascript:` 링크가 살아남고, 코드블록·목록은 스타일 없이 intent만 붙고, 표는 평탄화된다. 그래서 fixture(GFM 코드블록, 표, 체크리스트, 악성 HTML, `javascript:`·`https:` 링크, 외부 이미지)를 F-PR-5 규칙대로 그리는 데 **몇 줄이 들었는지**와 남은 결함을 잰다
- **P-SEL 줄 범위 선택 (F-AI-1):** 드래그로 여러 행을 선택하고 화면 밖으로 자동 스크롤한다. 결과 `Selection`을 stderr에 출력한다
- **P-COPY 텍스트 선택·복사:** 행을 가로지르는 글자 단위 선택과 ⌘C. 붙여 넣은 내용이 원본과 같은가. WebKit은 공짜이고 테이블은 직접 만들어야 한다
- **P-FOCUS (M0-3):** 터미널에서 실행했을 때 창이 앞에 오고 키 입력(예: `j`로 다음 파일)을 받는가
- **P-AX:** VoiceOver용 접근성 트리가 있는가. System Events로 창의 UI 요소를 조회해 diff 행 텍스트가 보이는지 확인한다
- **IME와 Mermaid는 기록만 한다:** 프레임워크 문서와 알려진 이슈로 적는다. Mermaid 혼합 구조는 Explain 탭을 열면 WebKit 헬퍼 3개가 돌아오므로, 그 메모리를 W 수치로 대신 적는다

### 판단 기준 (W 기준값을 잰 뒤, 네이티브 결과를 보기 전에 숫자를 확정한다)
1. 15만 줄 첫 화면 중앙값 ≤ W 중앙값, 좋은 프레임 ≥ 99%
2. footprint 합 중앙값이 W보다 **50% 이상** 적다 (W 기준값을 잰 뒤 확정)
3. P-MD·P-SEL·P-COPY·P-FOCUS가 W보다 많이 어렵지 않다. P-AX가 가능하다
4. 배포: 실행 파일 하나(또는 `.app` + 심링크), 바이너리 < 15MB, 가능하면 `cargo install`. 외부 툴체인(Metal)이 빌드에 필요하면 감점으로 적는다
5. **M2~M7 개발 속도:** 기능(PR 패널, 줄 옆 코멘트, 스트리밍 답변과 인용 링크, 검색, 좌우 보기, 구문 강조, Explain) × 스택마다 "공짜 / 크레이트 있음 / 직접 작성"을 표로 적는다
- 코드 줄 수는 참고로만 적는다(분모: W의 UI 코드 약 650줄 = app.js·css·html·main·protocol·events)

### W 기준값 (2026-10-13, `spike/bench.sh` 5라운드, 20회 모두 정상. 중앙값 [범위])

- 새 "좋은 프레임" 정의(<50ms이고 blank 아님)로는 W도 3.6~7.5%를 놓친다. 점프 뒤 청크 도착을 기다리는 프레임이다

### 확정한 판단 기준 (네이티브 결과를 보기 전)

## 결과: 측정 전에 중단 (2026-10-13)
사용자가 네 버전의 코드를 보고 실험을 끝냈다. 결론은 **B(Swift AppKit + Rust 코어)가 가장 깔끔하다**이다. 성능 측정(위 판단 기준 1·2)과 프로브 검증은 하지 않았다.

중단 시점의 상태 (UI 코드 줄 수, 공통 코어 제외):
| | 상태 | 코드 |
|---|---|---|
| A Rust + objc2 | 작성 중 (리뷰를 백그라운드 스레드로 옮기던 중) | 1,263줄 |
| **B Swift + Rust staticlib** | `build.sh`로 `build/griiy-b` 빌드 성공, `visual` 저장소 스크린샷 있음. 트리 작성 중 | **875줄** (Swift 4파일 + C 헤더 + core + 스크립트) |
| C gpui | Metal 툴체인 설치 뒤 앱 작성 시작 | 1,054줄 |

- 언어가 두 개(Swift, Rust)가 되고, C ABI 경계(opaque handle, JSON 문자열의 할당·해제 규약)가 생긴다
- 빌드는 `cargo build`에 `swiftc`를 더한 스크립트다. **`cargo install griiy`는 할 수 없다.** 배포는 `.app`(서명·공증) + Homebrew로 간다. PRD §6.1 F-IN-4 / M0-3 / M4-3을 고쳐야 한다
- 그 대신 AppKit을 쓰므로 NSTableView 행 재사용, `NSAttributedString` markdown, 접근성, IME, 포커스를 공짜로 얻는다. WebKit 헬퍼 3개(footprint 약 50~100MB)가 사라질 것으로 예상하지만, 측정하지는 않았다
- Mermaid(M7 Explain)는 그 탭에만 WKWebView를 쓰는 혼합 구조가 필요하다
